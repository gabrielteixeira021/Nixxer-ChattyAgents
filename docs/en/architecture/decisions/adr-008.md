# ADR 008: Tool Authority Stays Outside Persona

- **Status:** Accepted; queued for PE5
- **Date:** 2026-10-07
- **Decision owner:** Gabriel Teixeira
- **Record author:** Codex
- **Milestone:** PE5
- **Commitment:** owner commits; maintainers agree

## Context

SophIA must behave as both a configurable character and a useful assistant. For
the same request, one personality may answer affectionately while another may
complain or tease. The inherited engine also parses narrative model output into
state mutations and describes prompt guidance as a safety boundary. Neither is
sufficient authority for desktop tools, credentials or external effects.

## Decision

Persona Engine may realize immutable action facts in the configured character
voice. It does not own credentials, permission decisions or executors, and its
natural-language output is never executed directly.

The SophIA agent core owns a typed pipeline:

1. produce a structured, allowlisted intent;
2. validate arguments and permission policy;
3. obtain confirmation when the policy requires it;
4. execute the tool and receive a structured `ToolResult`;
5. provide that immutable result to Persona Engine for verbal realization.

Personality may control tone, vocabulary, honorifics, affection, sarcasm,
verbosity and theatrical reluctance. In the MVP, reluctance does not cancel a
safe authorized action. SophIA may announce intent before execution in future
tense, but can claim success only after `ToolResult.status == success`.

## Impact analysis

- **Direct:** future Persona realization contract and SophIA tool orchestrator.
- **Indirect:** prompts, memory retrieval, TTS and connector error handling.
- **Security:** typed allowlists replace prompt-only command safety.
- **Privacy:** credentials and connector tokens never enter persona prompts.
- **Rollback:** remove the tool slice and its realization contract; PE4 memory
  and ordinary conversation remain functional.

## Alternatives rejected

- Let the LLM emit shell commands: rejected because prose is untrusted and
  cannot enforce permissions or argument validation.
- Let Persona Engine execute tools: rejected because it mixes character
  expression with credentials, policy and operating-system effects.
- Generate a success response before execution: rejected because failure would
  make SophIA lie about external state.
- Make personality decide confirmations: rejected because security policy must
  remain invariant across character configurations.

## Risks

| Risk | Probability | Impact | Mitigation | Owner | Status |
|---|---|---|---|---|---|
| Prompt or memory attempts privilege escalation | Medium | High | Typed allowlist and policy outside Persona | Agent-core maintainer | Queued for PE5 |
| Persona changes validated arguments | Medium | High | Pass immutable intent/result facts to realization | Integration maintainer | Queued for PE5 |
| False success claim | Medium | High | Result-first narration tests for failure/cancel/denial | Quality owner | Queued for PE5 |
| Credentials leak into prompt or logs | Low | Critical | Connector-owned secret storage and redaction | Security owner | Queued for PE6 |

## Consequences

The first PE5 proof is an allowlisted `open_url` action such as opening Google.
Contrasting personalities must produce different responses while spies prove
the same tool, arguments, permission decision and factual outcome. Google
Calendar follows in PE6 with explicit authorization and mutation confirmation.
